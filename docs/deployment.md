# Deployment

## Neon and Prisma

Create separate Neon projects for staging and production. Select PostgreSQL 17 for the supplied backup image, or update the PostgreSQL client image to match the source major. Enable a supported recovery window and verify the plan's retention and operational guarantees. Pick a region near the service and verify connectivity and compliance needs. [Neon history window](https://neon.com/docs/postgres/backup-restore/history-window)

1. Obtain the pooled API URL and set `DATABASE_URL` only in the API service. Use a separate restricted pooled `DATABASE_URL` in the worker. The hostname for pooled Neon URLs contains `-pooler`. Keep TLS enabled, preferably using provider-supported full hostname verification.
2. Obtain the direct migration-owner URL and supply it as `DIRECT_URL` to the release task. Run `bun run db:deploy`. The migration role needs permission to install the supported `btree_gist` extension. Create dedicated login roles for API, worker, backup, and read-only monitoring using the provider's recommended role setup. Avoid application roles inheriting the owner role or `neon_superuser`.
3. Apply `psql -X -v ON_ERROR_STOP=1 -v api_role=rental_api -v worker_role=rental_worker -v backup_role=rental_backup -f scripts/db/grants.sql` over the direct migration connection. Set that connection through operator-managed libpq environment configuration. Supply the direct, separate backup role's URL to the backup job as `BACKUP_DIRECT_URL`. Reapply reviewed grants when adding a table or service operation.
4. In staging, exercise the same restricted roles as production and verify migrations and recoverability. Inject URLs at runtime through secrets. Keep migration and backup credentials out of ordinary owner routes. [Neon connection methods](https://neon.com/docs/connect/connect-from-any-app)

Apply `scripts/db/monitor-grants.sql` through the migration connection with `-v monitor_role=rental_monitor`. Reapply both grant scripts after schema upgrades. Upgrade an existing development checkout with `bun run db:generate` and `bun run db:deploy`, then restart API and worker. The operational-health migration is additive. Local verification does not apply it to the configured Neon database automatically.

## Services

- Build `docker build --target app -t rentledger .`, `docker build --target worker -t rentledger-worker .`, and `docker build --target backup -t rentledger-backup .`. The app image serves the built Vite UI on the same origin as the Hono API. Route HTTPS through a trusted proxy, preserve the configured public origin, overwrite the trusted client-IP header, and keep port 3000 inaccessible to direct public traffic. Use `/ready` for database readiness and `/health` for process liveness.
- Run a separate persistent worker using `rentledger-worker`. Give it the worker database role, messaging configuration, and `WORKER_HEARTBEAT_URL`. Production refuses an absent external heartbeat destination. The worker image uses durable database and external health checks rather than an API HTTP probe. Its PostgreSQL jobs survive process restarts. Forward structured logs and maintain a documented on-call owner. Set a graceful termination window of at least 35 seconds.
- Run the backup image hourly from an independent scheduler and monitor verified uploads through an external dead-man's switch. Use an independent restricted R2 bucket. Follow the [backup and recovery runbook](backup-recovery.md).
- Set `APP_ORIGIN`, a generated Better Auth secret, `SMTP_URL`, `MAIL_FROM`, and `TRUSTED_PROXY_IP_HEADER`. Configure SMTP and validate verification, password recovery, session expiry, and TOTP before inviting real owners. Run the onboarding command from the operator environment with the migration or a dedicated provisioning role.
- For the initial four rooms, one small persistent app service, one worker, managed Neon and a separate scheduled backup runner provide a low-complexity footprint. Verify real plan pricing and background-process limits before purchase. Scale processes and pooled connections after load tests. Track worker lag, database latency, organization-level volume, and export size before increasing limits.

## Worker troubleshooting

Worker failures log the operation stage, Prisma error code, SQLSTATE (when available), and a recognized database error category. Raw error messages, connection URLs, SQL and tenant data are excluded. `DatabaseNotReachable` indicates a connection or DNS failure; check the network and Neon endpoint availability before changing migrations. For the Node PostgreSQL runtime adapter, use `sslmode=verify-full` in `DATABASE_URL` to explicitly require certificate and hostname verification and avoid the driver's warning about future `require` semantics. [PostgreSQL SSL modes](https://www.postgresql.org/docs/current/libpq-ssl.html)

The durable heartbeat advances at most once per minute, after a complete successful polling cycle. Settings shows `UNAVAILABLE` before the first successful cycle and `OVERDUE` after three minutes without success. It lists only the owner's failed rent-generation months, with authorized, audited retries. `bun run worker:monitor` exits nonzero for a stale heartbeat, failed billing jobs, or failed/uncertain receipts and posts a minimal event to `WORKER_ALERT_URL`. The production monitor requires that alert destination. Alert receivers must implement the documented JSON POST contract; verify actual notification delivery and escalation in staging. A dead-man's switch must detect missing external heartbeat posts if the host or scheduler stops.

## Native Linux worker and independent scheduler

`ops/systemd/` contains a persistent worker service, an hourly backup timer, a fifteen-minute overdue-backup monitor and a one-minute worker monitor. These are deployment templates; they have not been installed or enabled by repository verification. Review them for the target Linux host and its Bun path before activation.

1. Install Bun 1.4.4, Node.js 24 and PostgreSQL clients compatible with the source major. Place the reviewed checkout and installed dependencies at `/opt/rentledger`, owned by the deployment operator. Create an unprivileged `rentledger` service account. Apply migrations and grants using the release role before starting services.
2. Create `/etc/rentledger/worker.env` with `NODE_ENV=production`, the restricted worker `DATABASE_URL`, `WORKER_HEARTBEAT_URL`, and authorized messaging configuration. It does not need migration, SMTP or backup credentials.
3. Create `/etc/rentledger/backup.env` with `NODE_ENV=production` and the backup variables described in the recovery runbook. Keep the independent storage credentials and encryption key in this operator-managed secret file or inject them from a secret manager.
4. Create `/etc/rentledger/monitor.env` with `NODE_ENV=production`, read-only monitoring `DATABASE_URL` and direct `BACKUP_DIRECT_URL`, `WORKER_ALERT_URL`, and `BACKUP_ALERT_URL`. It needs no tenant, sender, storage or encryption secrets. Give secret files mode 0640 with access restricted to the service account/operator.
5. Install the reviewed units under `/etc/systemd/system/`, run `systemctl daemon-reload`, then enable `rentledger-worker.service`, `rentledger-backup.timer`, `rentledger-backup-monitor.timer`, and `rentledger-worker-monitor.timer` with `systemctl enable --now`. Inspect `systemctl list-timers` and service journals. Trigger one manual backup and an isolated off-site restore, then interrupt a worker/backup schedule in staging and confirm the external alerts arrive.

Run backup scheduling outside the web container lifecycle. For a separate backup host, install the backup and monitor units there with only their own credentials. Configure an external dead-man's switch so losing that entire host still alerts an operator. A sleeping web host or a timer file alone does not establish operational backup protection.

## Launch gates

Verify HTTPS and mail in the selected staging environment, apply migrations using separate credentials, run the isolation and browser suites, and exercise restricted roles. Confirm production R2 encryption keys, lifecycle and bucket locks, external failure and overdue alerts, and an isolated restore from the actual off-site copy. Approve the shared sender arrangement, tenant consent and Meta templates before enabling WhatsApp. Review current dependency advisories and verify Docker images in CI. Production services remain unconfigured until those checks and credentials are available.
