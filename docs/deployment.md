# Deployment

## Neon and Prisma

Create separate Neon projects for staging and production. Select PostgreSQL 17 for the supplied backup image, or update the PostgreSQL client image to match the source major. Enable a supported recovery window and verify the plan's retention and operational guarantees. Pick a region near the service and verify connectivity and compliance needs. [Neon history window](https://neon.com/docs/postgres/backup-restore/history-window)

1. Obtain the pooled API URL and set `DATABASE_URL` only in the API service. Use a separate restricted pooled `DATABASE_URL` in the worker. The hostname for pooled Neon URLs contains `-pooler`. Keep TLS enabled, preferably using provider-supported full hostname verification.
2. Obtain the direct migration-owner URL and supply it as `DIRECT_URL` to the release task. Run `bun run db:deploy`. The migration role needs permission to install the supported `btree_gist` extension. Create dedicated login roles for API, worker, and backup using the provider's recommended role setup. Avoid application roles inheriting the owner role or `neon_superuser`.
3. Apply `psql -X -v ON_ERROR_STOP=1 -v api_role=rental_api -v worker_role=rental_worker -v backup_role=rental_backup -f scripts/db/grants.sql` over the direct migration connection. Set that connection through operator-managed libpq environment configuration. Supply the direct, separate backup role's URL to the backup job as `BACKUP_DIRECT_URL`. Reapply reviewed grants when adding a table or service operation.
4. In staging, exercise the same restricted roles as production and verify migrations and recoverability. Inject URLs at runtime through secrets. Keep migration and backup credentials out of ordinary owner routes. [Neon connection methods](https://neon.com/docs/connect/connect-from-any-app)

## Services

- Build `docker build --target app -t rentledger .` and `docker build --target backup -t rentledger-backup .`. The app image serves the built Vite UI on the same origin as the Hono API. Route HTTPS through a trusted proxy, preserve the configured public origin, overwrite the trusted client-IP header, and keep port 3000 inaccessible to direct public traffic. Use `/ready` for database readiness and `/health` for process liveness.
- Run a separate persistent worker from the app image with `bun apps/worker/src/index.ts`. Give it the worker database role and messaging settings only. Its PostgreSQL jobs survive process restarts. Forward structured logs, alert on missing worker heartbeat and repeated failures, and maintain a documented on-call owner. Set a graceful termination window of at least 30 seconds.
- Run the backup image hourly from an independent scheduler and monitor verified uploads through an external dead-man's switch. Use an independent restricted R2 bucket. Follow the [backup and recovery runbook](backup-recovery.md).
- Set `APP_ORIGIN`, a generated Better Auth secret, `SMTP_URL`, `MAIL_FROM`, and `TRUSTED_PROXY_IP_HEADER`. Configure SMTP and validate verification, password recovery, session expiry, and TOTP before inviting real owners. Run the onboarding command from the operator environment with the migration or a dedicated provisioning role.
- For the initial four rooms, one small persistent app service, one worker, managed Neon and a separate scheduled backup runner provide a low-complexity footprint. Verify real plan pricing and background-process limits before purchase. Scale processes and pooled connections after load tests. Track worker lag, database latency, organization-level volume, and export size before increasing limits.

## Launch gates

Verify HTTPS and mail in the selected staging environment, apply migrations using separate credentials, run the isolation and browser suites, and exercise restricted roles. Confirm production R2 encryption keys, lifecycle and bucket locks, external failure and overdue alerts, and an isolated restore from the actual off-site copy. Approve the shared sender arrangement, tenant consent and Meta templates before enabling WhatsApp. Review current dependency advisories and verify Docker images in CI. Production services remain unconfigured until those checks and credentials are available.

Local verification on 5 November 2026 used PostgreSQL 17 with three Prisma migrations and separate restricted API, worker, and backup roles. Prisma reported no schema drift. Fifteen unit and integration tests passed, covering organization isolation, authentication and TOTP, ledger concurrency, WhatsApp callback reconciliation, and bounded retry. The mobile Playwright flow passed through sign-in, rental setup, cash and online payments, scoped CSV export, and sign-out. Lint, type checking, the production web build, and the dependency audit also passed. The local mail adapter produced both onboarding links. The backup runbook records the encrypted restore results. Neon, SMTP, Meta, R2, hosted scheduling and Docker execution require verification in the target environment.
